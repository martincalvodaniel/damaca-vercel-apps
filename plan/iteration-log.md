## AGW-02 — Generación de apps con Turborepo

- Cambios: `bun run generate:app` ejecuta `turbo gen app`, con preguntas o respuestas por `--args`; la base `mongo-google` conserva Better Auth, Google, MongoDB y gestión de acceso; `local-pwa` conserva IndexedDB, exportación e instalación offline. Ambos modos generan identidad, puerto, instrucciones específicas y planificación de producto. Se excluyen `.env.local`, `.vercel`, dependencias y artefactos de build.
- Evidencia: `bun run test:generator` pasa 6 casos y 37 aserciones; ambas apps temporales generadas pasan type-check, y sus pruebas pasan (local: 14; MongoDB: 37). Las apps temporales se retiraron después de comprobar los resultados.
- Validación: generación interactiva con puerto predeterminado 3007 y por argumentos para ambos modos; los tests rechazan colisiones, entradas inválidas y destino ocupado, preservan archivos existentes y comprueban enlaces/documentos. El build local pasa mediante el filtro raíz y su exportación contiene 47 recursos de shell offline. El build MongoDB pasa con `next build --webpack`. En navegador, Settings y Home siguen cargando desde la caché y permiten navegar con el preview detenido. `bun install --frozen-lockfile`, `git diff --check` y Biome pasan sin errores.
- Límites: el build MongoDB mediante Turbo/Turbopack no pudo ejecutarse porque el sandbox denegó un proceso auxiliar (`Operation not permitted`); el mismo código compiló con Webpack. No se probaron credenciales OAuth reales ni conexión a una base MongoDB externa. Biome conserva 14 warnings presentes en las bases copiadas; no hubo errores.

<a id="agw-05-google-identity-and-hub-access"></a>
## AGW-05 — Google identity and Hub access

- Alcance: [aceptación AGW-05](iterations.md#agw-05--google-identity-and-hub-access-shared-package). `@damaca/identity` es el primer paquete compartido bajo `packages/*`: proveedor Google/OIDC central del Hub, consumidores Next.js, lectura/renovación de sesión, cliente de permisos, UI de acceso/cuenta y worker de red. Pocha Score y Card Wars lo consumen; las otras apps y los dos scaffolds mantienen su comportamiento.
- Decisión final del usuario: login obligatorio y permiso por app, con Google configurado únicamente en Hub. Se adopta `@better-auth/oauth-provider` 1.7.12, callbacks exactos por cliente/entorno, S256 PKCE, state/nonce, validación de firma/emisor/audiencia y sesiones/cookies independientes. UserInfo obtiene la aplicación del token y consulta catálogo activo y permiso vigente; no acepta emails afirmados por consumidores ni concede acceso implícito a administradores.
- Persistencia: Hub usa el adaptador nativo MongoDB para usuarios, cuentas, sesiones, códigos, tokens y claves cifradas; índices únicos/de consulta/caducidad registrados en su capa DB. Cookies anteriores requieren reautenticación. Los consumidores usan cookies independientes y no necesitan MongoDB. Las credenciales permanecen en cada entorno; solo se añaden ejemplos ficticios.
- Renovación: Server Components solo leen la cookie cifrada de cuenta; la renovación ocurre en Route Handlers para que el navegador reciba las cookies rotadas. La lectura interna y los endpoints HTTP de devolución/renovación de tokens están cerrados al navegador; el protocolo sigue validándose servidor a servidor.
- Datos/PWA: IndexedDB, reglas, copias y registros existentes no se modifican ni migran. La instalación se conserva; el producto requiere conexión. El worker de red retira exclusivamente las cachés antiguas de su app y nunca almacena HTML/RSC/API autenticados. Las copias ya distribuidas necesitan reconectar y recargar. Cerrar sesión no elimina partidas; cuentas del mismo navegador siguen compartiendo datos locales sin cifrado ni sincronización.
- Integración de alojamiento: raíces Vercel conservadas; el Hub exceptúa únicamente los endpoints OIDC de máquina de la restricción geográfica para permitir llamadas desde servidores `cdg1`. Navegación, autorización y callback Google conservan la restricción. Prueba de rutas cubre la excepción y sus límites; no se ha modificado infraestructura remota ni promovido producción.
- Validación local: instalación `bun install --frozen-lockfile`; tipos de las tres apps y el paquete; builds de producción mediante filtros raíz (4 tareas, incluido paquete); 76 pruebas pasan (Hub 19, Pocha 22, Card Wars 20, identidad 15), sin fallos; generador 6 pruebas/37 expectativas. La integración OIDC usa handlers reales por HTTP local, identidad ficticia y adaptador de memoria: login, permisos, revocación, aislamiento, renovación, códigos repetidos, callback/cliente incorrectos, firma/nonce/emisor/audiencia incorrectos, PKCE/secreto incorrectos, rotación y sesión central retirada. El test de worker ejecuta el código generado y comprueba retirada acotada de cachés y red obligatoria para rutas, RSC y APIs.
- Transporte: simulación Postman local desde el contrato UserInfo; el cliente real obtiene aprobado, denegado por revocación, denegado por 401 e indisponible por 500 HTML. El log observó cuatro peticiones al miembro Hub. Especificación YAML parseada y contrato comprobado; no se creó ni publicó workspace Postman. La generación del mock escribió los archivos pero terminó con un error de llavero macOS; `postman spec lint` quedó bloqueado por el mismo error. Creación y ejecución de la simulación sí funcionaron.
- Navegador: previews compilados con configuración ficticia en 3103 (3003 estaba ocupado y se preservó) y 3004. Card Wars redirige de Home a login; Pocha redirige de Settings a login. Pantallas legibles en escritorio y 390×844; botón Google recupera un error cuando Hub no está disponible. Pestañas/servidores temporales cerrados. No se acredita interacción de producto autenticado ni instalación nativa en esta sesión.
- Incidentes de build resueltos: Turbopack del Hub falla creando un proceso/puerto auxiliar incluso al reintentar; se usa Webpack como las dos apps consumidoras. Una primera ejecución con `-- --webpack` llegó también a `tsc` del paquete y fue rechazada; el script del Hub ya selecciona Webpack y el comando raíz normal pasa.
- Límites de rollout: no se ejecutó Google real, persistencia MongoDB entre reinicios, callbacks desplegados, WAF remoto ni migración de un worker antiguo en navegador. La prueba MongoDB desechable se amplió para permisos/revocación/app inactiva, pero no se ejecutó sin servidor aislado disponible. Deben configurarse clientes/callbacks y secretos según [la guía compartida](../packages/identity/README.md) y verificar esos entornos antes de activar el cambio. Estos checks no se contabilizan como pases locales.
- Documentación: planes e instrucciones vigentes actualizados y enlazados desde los tres ámbitos, con registro principal único aquí. Rutas Markdown locales, Biome de archivos editados/nuevos y `git diff --check` revisados. Las validaciones con servicios externos se distinguen de la aceptación de implementación local.
- Publicación: el SHA y su coincidencia con `refs/heads/int` remoto se verifican en Git durante el cierre; `main` permanece bajo gestión humana.
- Capacidad antes del cierre: 45% de 5h y 91% de 7d restantes; reserva mínima respetada. La lectura final se comunica después de verificar publicación.
